** Installing at work, in order

Assumes the tasks in Part 8 have landed on =main= in both repos.  Part
7 has the checks for each step.

1. Admin account, Xcode command-line tools, =gh auth login= with the
   work GitHub account (=GH_HOST= for GitHub Enterprise).
2. =git clone https://github.com/chiply/.files ~/.files=.
3. Create =~/.zshenv.local= from the work example in Part 6 --
   =DOTFILES_PROFILE=work=, the three =INCLUDE_*= gates off.  No
   1Password token, ever.
4. =~/.files/bootstrap.sh=: with the profile set it links everything
   but the manifest, brews everything but the personal list, registers
   no Syncthing folder, installs no LaunchAgent, clones .zetta.d and
   copies =templates/zetta.work.el= to =~/.zetta.el=.
5. Confirm =~/.zetta.el= is the work template (=head -3=).  If the
   bootstrap ran before WP-F3 landed: =cp ~/.zetta.d/templates/zetta.work.el ~/.zetta.el=.
6. Write =~/.private.el= from the draft in Part 3 and =~/.authinfo.gpg=
   with the work GitHub token (and an LLM key if the employer allows
   one).  =chmod 600= both.
7. =cd ~/.zetta.d && bin/zetta install= (about an hour: every package
   builds locally), then =bin/zetta test= and =bin/zetta doctor=.
8. First GUI launch; run the day-one checks (Part 7).
9. =git config --global github.user <work login>=; =M-x copilot-login=
   if there is a seat; =M-x org-jira-get-issues= once
   =zetta-jira-url= is set.

If the machine must be set up before Part 8 lands, the manual path is
the same list with step 4 replaced by: run =main.py= after deleting the
manifest's paths from a scratch copy of =files/=, =brew bundle= on a
Brewfile with the personal block removed, clone .zetta.d by hand, and
skip every LaunchAgent.  Not recommended: the tasks are small.

* Part 1 — What "work" means here

The headless profile was capability-driven (no SVG, no toolchain) and
lives in predicates (=zetta-module-conditions=), so one user file is
right on every machine.  The work profile is policy-driven: the modules
are perfectly able to run; they must not.  Policy belongs in the user
file, hence a template and not a predicate.

Three rules sorted every module (Part 2.1 applies them):

- R1 -- it reads or writes a *personal account or service*: mail, feeds,
  read-later, social, chat, music, dictation, web search on personal API
  keys.  Out.
- R2 -- it moves data between this machine and *personal
  infrastructure*: Syncthing, the hub, the personal retrieval servers,
  the kb pipelines, Logseq/iPad sync.  Out.
- R3 -- it is a *toy*, or it reveals *location*.  Out.  (The two
  cosmetic toys in =:ui= stay: they draw a cat and a bird.)

Everything else stays, by the owner's decision of 2026-09-13: the org
task system and hyperbole/hywiki (re-rooted on a work kb, Part 3), the
AI stack (on work keys, Part 5), Jira and Slack (parameterised, Part 5;
Slack's token model is the one thing to clear with the employer, Part 9).

** 2.4 Why an inclusion list for :app

=zetta--resolve-module-spec= treats a list with any =-name= as
exclusions and any other list as inclusions; mixing is an error.  =:app=
keeps 17 of 42 files, so the inclusion form is shorter and, more to the
point, *closed*: a new personal app added to =modules/app/= later does
not silently join the work profile.  The three exclusion lists
(=:completion=, =:tools=, =:org=) are open in the other direction, which
is the right default for developer tooling.

* Part 4 — Secrets: a backend the employer's vault can plug into

Owner's requirement (2026-09-13): the employer may use a different
vault; make things amenable to adopting it without knowing what it is.

** Requirements

- R-S1: no personal token on the work machine, ever.
- R-S2: an unknown work vault -- 1Password Business, Bitwarden, HashiCorp
  Vault, AWS Secrets Manager, =pass=, or just =~/.authinfo.gpg= -- is
  adoptable by editing ~/.zetta.el and ~/.private.el only.
- R-S3: the decision is made *per machine* (in ~/.zetta.el), and
  =init.el= honours it rather than sniffing for an =op= binary.
- R-S4: the personal machine keeps today's behaviour with no edit.
- R-S5: CI and the hub keep theirs (=auth-sources nil=).

** Design

Today (=init.el:19-109=): a cache filled by =zetta-op-load= (which
~/.private.el calls at line 30), read by =zetta-op-read=, and an
auth-source backend =zetta-op= that serves the same cache to forge,
gptel, slack, erc and mastodon through =zetta-op-auth-source-entries=.
The design keeps all of it and adds one decision variable and one
generic loader.

In =bootstrap-modules.el= (the user-variables section, so ~/.zetta.el
can set them):

#+begin_src emacs-lisp
(defvar zetta-secrets-backend nil
  "How ~/.private.el and auth-source get their secrets.  Set in ~/.zetta.el.
nil        pick `op' when the `op' binary and `zetta-op-template-file'
           both exist, else `authinfo'.  (Today's behaviour.)
op         1Password CLI: one `op inject' over `zetta-op-template-file'.
command    run `zetta-secrets-command'; it prints KEY=VALUE lines.
authinfo   Emacs's own auth-source files; no cache, no subprocess.
none       no secrets at all: `auth-sources' is nil (CI, the hub).")

(defvar zetta-op-template-file
  (expand-file-name "source/op-secrets.env.tpl" user-emacs-directory)
  "Template `op inject' resolves.  A work vault points this outside the
repo, e.g. ~/.config/zetta/secrets.env.tpl with op://<WorkVault>/... refs.")

(defvar zetta-secrets-command nil
  "Shell command for the `command' backend.  Must print KEY=VALUE lines.")
#+end_src

In =init.el=: =zetta-secrets-load= replaces the body of =zetta-op-load=
(op builds the command as =op inject -i TEMPLATE=; =command= uses the
variable; both parse the same =KEY=VALUE= lines into the same cache);
=zetta-op-load= and =zetta-op-read= become aliases, so the personal
private file needs no edit (R-S4).  The auth-source parser is
registered, and =auth-sources= set to =(zetta-op)=, only for =op= and
=command=; =authinfo= leaves =auth-sources= at Emacs's default
(=~/.authinfo=, =~/.authinfo.gpg=, =~/.netrc=); =none= sets it nil.  The
decision reads =(zetta-secrets-effective-backend)= -- the variable, or
the nil rule -- *after* ~/.zetta.el has loaded, which it already does
(line 18 loads the user file; the backend block is at 102-109).

The private file's contract is unchanged: it calls =(zetta-op-load)=
(or the new name) when it wants the cache, and =zetta-op-read= for
each value; with =authinfo= it calls =auth-source-pick-first-password=

** Deviations from the plan, with reasons

- *The secrets code lives in =source/bootstrap/bootstrap-secrets.el=*,
  required by init.el at the point the plan put it (after ~/.zetta.el),
  not inline in init.el: a file of its own can be loaded alone by the
  batch tests and by =doctor=.  =zetta-secrets-effective-backend= is in
  bootstrap-modules.el next to the variables, for the same reason.
- *=zetta-ai-personal-backends= is a defvar in ai.el*, not in
  bootstrap-modules.el: the template's setq runs before the module, so
  the defvar keeps the value, and the variable stays next to what it
  gates.
- *WP-Z9 uses one fallback idiom instead of a root variable per
  package*: the standalone zettapkg packages default their files under
  =(or (bound-and-true-p zetta-kb-dir) "~/kb/")=, the config's root when
  loaded there and ~/kb under =emacs -Q= for their tests.  The checker
  recognises that form structurally and reports every other literal;
  the doc had left the mechanism open.
- *=doctor= reads the profile and backend through a batch Emacs*
  (bootstrap-modules.el then ~/.zetta.el, no module), not by parsing
  the file: a =setq= inside a condition would defeat a grep, and it is
  the same code init.el runs.  Consequence: the user file must load
  standalone; the templates do.
- *The rehearsal ran under the source-built Emacs 32.0.50*, not
  emacs-plus 31 as Part 7.2 says: the elpaca builds are compiled by 32
  (bytecode census), and 31 against them replays the version-skew saga.
  The full profile's run got a private copy of ~/kb (300 MB) in its
  scratch HOME rather than a symlink, so nothing could write into the
  synced tree.
- *The Brewfile gates needed a new mechanism* (audit S12): =brew=
  filters the environment, so the profile and the two build gates
  travel as =HOMEBREW_*= mirrors exported by .zshenv, .zshrc and
  bootstrap.sh.  The two existing gates had never fired under =brew
  bundle=.
- *No =DRY_RUN= in bootstrap.sh* (WP-F3's done-when offered inspection
  as the alternative): four =if personal= blocks and one helper,
  verified by an awk pass and a unit test of the helper.
- *=python3= for main.py in bootstrap.sh* and a =#!/bin/bash= on the
  distros script: one-word robustness fixes met on the way.
- *WP-F2's "4 skips" is 13*: the manifest's wallpaper glob alone
  matches five files, and the untracked news-reader state is listed
  too.
- *WP-Z12's ci-test exits 1 on a gate that is not the rehearsal's*:
  =LOCK-MISSING= for poimap, unpinned since bd9100e (2026-09-12).  Both
  templates reach ZETTA-OK with zero use-package errors, which is the
  done-when; the pin is the owner's =bin/zetta freeze= in the PR.
