** Verdict [2026-09-13]

Both repos are public (measured, =gh api=: .zetta.d 13 stars, 1 fork;
.files 4 stars, 0 forks).  *Nothing secret is in either tracked tree
today* (measured: value-pattern scan over every tracked file in both

Beyond the history the risks are of a different kind, and they are what

PR per repo); harden =security.el=, file modes and the pre-commit hook;
adopt the profile in work-profile.org.  Rotating the four credentials
and rewriting history are *separate steps*, deliberately outside the
work prep (owner, 2026-09-13): the values are already public, and
cloning the repos onto one more machine changes nothing about that.
Part 3 has the tasks with a "done when" each; group A specifies the

* Part 1 — Scope and method

** What was audited

- The tracked trees at the =dev= heads: .zetta.d at 7b1242a (595 tracked
  files, 320 of them modules) and .files (121 tracked files, three
  modified in the working tree).
- The full history of every branch: .zetta.d 1083 commits, .files 249
  (measured, =git rev-list --all --count=).
- The untracked machine state the install expects: ~/.private.el,
  ~/.zshenv.local, ~/.authinfo, ~/.mbsyncrc, the ~/.msmtprc symlink,
  ~/.maildir, ~/kb, ~/.ssh/config (host names only).
- GitHub repository settings: visibility, forks, secret scanning
  (measured, =gh api repos/<owner>/<repo>=).

** How

Tracked trees: =git grep= over every tracked file, both repos, excluding
the lockfiles.  History: =git log --all -p= filtered to added AND removed
lines (a removed secret was once an added one), the same patterns.  Two
pattern families:

- provider shapes -- Slack =xox*= tokens and =d=xoxd= cookies, GitHub
  =ghp_= / =gho_= / =github_pat_=, OpenAI =sk-=, AWS =AKIA=, 1Password
  =ops_=, Google =AIza=, JWTs, PEM private-key headers, =Bearer= headers,
  credentials embedded in URLs, =authinfo= machine/login/password lines;
- elisp shapes -- =setq= / =defvar= / =defcustom= / plist keys binding a
  symbol whose name ends in =password=, =passwd=, =secret=, =token=,
  =api-key=, =client-id= or =cookie= to a string literal.  (The first
  family alone misses every =(setq foo-password "...")=; this one caught
  all of S1.)

Identifier sweep over the tracked trees: e-mail addresses, phone numbers,
IPv4 and Tailscale ranges, host names, the two previous employers' names,
the previous laptop's host name, absolute home paths.  Reviewed by hand:
every module under =modules/= that names a URL, a port or a =~/= path
(measured list in work-profile.org Part 2), every file under
=.files/files/=, =bootstrap.sh=, =main.py=, the Brewfile, the
LaunchAgents, and both CI workflows.

No dedicated scanner was available: =gitleaks=, =trufflehog=,
=git-secrets= and =detect-secrets= are all absent (measured, =which=);
S9 puts one in the loop.

** Limits

- Text diffs only.  The PDFs once tracked under =.lit/pdf/= in .files
  were not content-scanned (they are papers; the concern is size and
  copyright, not secrets).
- The fork of .zetta.d is outside our control; whatever it holds stays.
- The employer's environment (MDM, proxy, vault) is unknown; S2, S6 and
  S7 are written for the general case.

** S2 [High for the work machine] The secrets design assumes one personal vault, unlocked by a long-lived token

Evidence: =init.el:108-109= sets =auth-sources= to the 1Password backend
whenever an =op= binary is on =PATH=; =source/op-secrets.env.tpl=
resolves 33 items from the personal =Dev= vault in one =op inject=;
=secrets.md= tells a new machine to export =OP_SERVICE_ACCOUNT_TOKEN=
from ~/.zshenv.local, which is how this Mac is set up (measured; the
file is mode 644, S5).

Impact at work: an employer-managed Mac (MDM, EDR, backup agents) that
holds that token can read every personal credential -- mail app
passwords, Reddit, Mastodon, Spotify, the works.  If the employer
installs 1Password CLI for its own vault, =init.el= silently switches
the backend on and =op inject= runs against the wrong account at every
start.  And the reverse: a work vault of unknown type has no way in
short of editing =init.el=.

Fix: work-profile.org Part 4 -- a =zetta-secrets-backend= chosen in
~/.zetta.el, a template path that can point outside the repo, and a
=command= backend for any vault that can print =KEY=VALUE= lines.  The
work profile never carries the personal token (its template sets the
backend to =authinfo=).

** S6 [Medium; breaks at work] core/security.el pins TLS trust to certifi, and can pin it to an error message

Evidence: =modules/core/security.el:16-28=.  It shells out =python -m
certifi= and installs the printed path as the *only* trust file
(=gnutls-trustfiles=, and =tls-program= for the external =gnutls-cli=),
with =gnutls-verify-error t=.  =shell-command-to-string= captures stderr
together with stdout, so when =python= exists but certifi is not
installed, the "trust file" is the interpreter's error text -- the exact
failure the file's own comment describes for the no-python case, one
step over.  Line 5 requires the obsolete =cl=.

Measured on this Mac: =python= is not on =PATH= (only =python3=), so the
block is inert here.  pyenv shims, a Homebrew =python= or an employer's
tooling make it live.  Behind a corporate TLS-intercepting proxy the
certifi bundle lacks the corporate root, so every =url-retrieve= (gptel,
forge, elpaca menu fetches, devdocs) fails while =git= (system trust)
keeps working -- a confusing split that looks like "Emacs is broken".

Fix (Part 3 C, WP-Z7): default to system trust (Emacs's gnutls already
reads the macOS and Homebrew bundles), only use the certifi path when
=file-exists-p= says it is a file, add =zetta-extra-trust-files= for a
corporate CA, keep =gnutls-verify-error t=, drop the =tls-program=
override and the =cl= require.
