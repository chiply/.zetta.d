#+author: Charlie Holland

Performance findings for the zetta config and the Emacs build under it.
Same rule as [[file:TODO.org][TODO.org]]: keep the evidence with the item so the next person to
look does not have to re-derive it.  Where a number is a measurement it says
so; where it is an inference it says that too.

Produced [2026-09-08] from a five-way audit (build, startup, redisplay,
runtime/GC, editing latency) plus direct measurement of the live daemon.
The investigation started from "Emacs keeps freezing -- is it native comp?"
The answer was no: *zero* native-compilation subprocesses were running and no
=.eln= had been written in two hours.  The freezes are GC pauses, and the
allocation that drives them comes from animation timers repainting SVG chrome.

** The idle profile

A 5 s =sample(1)= of a completely idle daemon put ~450/4200 samples here:

#+begin_example
wait_reading_process_output
 -> detect_input_pending_run_timers
    -> redisplay_preserve_echo_area
       -> redisplay_window -> redisplay_tab_bar
          -> lookup_image -> svg_load_image
             -> librsvg parse + cairo text fill
#+end_example

That is the whole story in one stack: timers wake Emacs ~19x/second, each
wake forces a redisplay, and each redisplay rebuilds the SVG chrome.

*Refinement from later measurement.*  Of the ~450 samples in that path, ~115
are in =svg_load_image= (librsvg rasterisation) and the remaining ~335 are the
elisp rebuild and redisplay machinery.  So rasterisation is roughly a quarter
of the cost and the *elisp rebuild is the bulk of it* -- which matters,
because it means the fix is memoisation in the renderer, not image caching.
An independent check could not reproduce sustained librsvg parsing at idle
(10 consecutive tab-bar renders were byte-identical; only 2 distinct strings
appeared over ~10 s, tracking the clock's minute hand), and the elisp
arithmetic alone accounts for the observed 11%.

** The economics of one SVG bar

Measured directly, and worth knowing before tuning anything in =modules/ui/=:

| Bar                              | cache hit | one char changed |
|----------------------------------+-----------+------------------|
| tab bar (1874x66, 21 =<text>=)     |   0.20 ms |          4.4 ms  |
| mode line (1665 B)               |   0.07 ms |          1.56 ms |

A cache hit is nearly free; *any* content change costs a full librsvg parse
plus fontconfig and cairo text layout.  So the cost is driven by how often the
string changes, not by how often redisplay runs.

The pure-elisp rebuild of every bar in every live window is *~6.4 ms per
redisplay pass* steady-state (14.3 ms including a first-render outlier), across
6 windows.  At ~20 timer wakeups/second that is ~128 ms/s, i.e. *~13% of a
core in elisp alone* -- independently the same order as the 11% =sample(1)=
attributed to the redisplay path.  The librsvg parses sit on top of that.

** Where the memory is

=vmmap -summary= against the 1.4 GB footprint:

| Region                   | Resident | What it is                                    |
|--------------------------+----------+-----------------------------------------------|
| =MALLOC_SMALL=           | 918 MB   | Lisp heap + 165 MB free-lists + fragmentation |
| =__TEXT=                 | 627 MB   | mapped code -- mostly *system frameworks*     |
| =mapped file=            | 519 MB   | frameworks, fonts, =.eln=                     |
| =dyld private memory=    | 245 MB   | loader bookkeeping (1091 regions)             |
| =MALLOC_LARGE (empty)=   | 52 MB    | 47 empty regions -- see [[*read-process-output-max is 64 MB globally][the 64 MB read buffer]] |
| /of which/ =.eln=-backed | 103 MB   | measured subset, see below                    |

*Correction, recorded because the first pass got it wrong.*  The 1199 mapped
=.eln= dylibs look like they should dominate =__TEXT=, and an early reading of
this table attributed ~600 MB to them.  Summing the =.eln=-backed regions
directly says otherwise:

#+begin_example
4605 regions   virtual 156.3 MB   resident 103.2 MB   dirty 27.3 MB
#+end_example

So native compilation costs ~103 MB resident, not ~600 MB.  The rest of
=__TEXT= is system frameworks -- WebCore 28.2 MB and JavaScriptCore 18.9 MB
(pulled in by =--with-xwidgets=), =__OBJC_RO= 60 MB, and the usual macOS set.
*Do not treat AOT native-compilation as a memory lever* -- dropping it would
recover far less than the raw =__TEXT= figure suggests.

The real oddity is not memory but compilation status: 1199 native-compiled
libraries are mapped into the process while the config's own 294 module files
run interpreted.

** DONE gc-cons-percentage is never restored, so it sits at the init value 0.6
:PROPERTIES:
:FOUND:    [2026-09-08]
:MODULES:  early-init.el, source/bootstrap/bootstrap-gcmh.el
:END:

The root cause of the GC numbers above.  Found independently by two auditors
and confirmed directly.

=early-init.el:11-13= raises the threshold and the percentage for init, and
=early-init.el:16-21= defines =zetta--restore-gc= to put *both* back:

#+begin_src emacs-lisp
(defun zetta--restore-gc ()
  (setq gc-cons-threshold (* 16 1024 1024)   ; 16MB
        gc-cons-percentage 0.1))
#+end_src

=bootstrap-gcmh.el:20-21= then removes that hook wholesale so gcmh can own the
threshold -- but gcmh only ever writes =gc-cons-threshold=, never the
percentage.  So the percentage half is silently lost.

#+begin_example
gc-cons-percentage => 0.6      gc-cons-threshold => 800000
live heap          => 209 MB
#+end_example

The effective trigger is =max(threshold, percentage x (live + since_gc))=
(=src/alloc.c:5740=), i.e. *~125 MB*.  gcmh's 800 KB low threshold is inert:
its "collect early and cheaply while idle" design never runs, and every GC
you feel is gcmh's explicit idle call sweeping a huge nursery.

*Action.*  Keep removing the hook, but do not lose its percentage half -- add
=(setq gc-cons-percentage 0.1)= to =bootstrap-gcmh.el='s =:config=.

*Caveat.*  Mark time scales with the /live/ set (209 MB), not with accumulated
garbage, so this makes collections more frequent and much shorter rather than
free.  Re-measure =gcs-done= and =gc-elapsed= after.


*Applied [2026-09-09]: `(setq gc-cons-percentage 0.1)' in bootstrap-gcmh.el's
:init, next to the threshold, with the alloc.c reasoning in a comment.
Re-measure `gcs-done' and `gc-elapsed' after a day's use.*

** DONE read-process-output-max is 64 MB globally
:PROPERTIES:
:FOUND:    [2026-09-08]
:MODULES:  modules/term/shell.el, early-init.el
:END:

=early-init.el:53= deliberately sets 4 MB with a comment saying why.
=modules/term/shell.el:3= then overrides it globally at top level:

#+begin_src emacs-lisp
(setq read-process-output-max (* 64 1024 1024))
(setq process-adaptive-read-buffering nil)
#+end_src

Live value is =67108864=, so the override wins.  The comment at
=modules/tools/lsp.el:4= claiming this is "handled in early-init.el" is now false.

In =src/process.c:973= the value is clipped only to =INT_MAX=, not to
=MAX_ALLOCA=, and is latched per process at creation.  =process.c:6267= then
does =SAFE_ALLOCA(carryover + readmax)=, which above ~16 KB becomes
=record_xmalloc= (=lisp.h:5629=).  So *every read from every subprocess mallocs
and frees 64 MB* -- on macOS an =mmap=/=munmap= pair plus page-fault churn, per
read, for copilot's streaming completions, =mu server=, and elfeed's curl.

This is visible in =vmmap= as 47 =MALLOC_LARGE (empty)= regions holding 52 MB.

*Action.*  Delete =shell.el:3= so early-init's 4 MB stands; set it buffer-locally
in a shell hook if shell buffers genuinely need more.  Reconsider
=process-adaptive-read-buffering nil= on line 4 -- also global, also every process.


*Applied [2026-09-09]: both globals removed from shell.el, so early-init's 4MB
stands.  `process-adaptive-read-buffering' is left at its default for the same
reason it was flagged: it applied to every process, not just shells.*

** DONE svg-line's renderers never memoize
:PROPERTIES:
:FOUND:    [2026-09-08]
:MODULES:  ~/source_code/svg-line/svg-line.el
:END:

=svg-line--render= (=svg-line.el:2144=) rebuilds unconditionally on every call.
The only cache in the file is =svg-line--freeze-cache= (=:1352=), gated solely
on =(active-minibuffer-window)=, and =svg-line-display= (=:1748=) allocates a
fresh =svg-image= spec every time.

So every bar in every window is rebuilt in full on every redisplay pass even
when the resulting string is byte-identical -- which, per the measurement
above, it usually is.  That is ~6.4 ms per pass across 6 windows, ~20 times a
second.

*Action.*  Hash the built SVG string per =(NAME . window)= and return the
previous propertized display string on a match.  Insert at =:2172= -- after
=svg-line--build-lines=, before =svg-line-display=.  Keep
=svg-line--store-placements= *outside* the short-circuit; placements must stay
live for hit-testing.

Note this is the DEV copy at =~/source_code/svg-line=, which is unpushed and
loaded live -- see [[file:~/.claude/projects/-Users-charlieholland--zetta-d/memory/svg-line-engine-features.md][the svg-line engine note]].  A restart wipes uncommitted work.


*Applied [2026-09-09]: `svg-line--display-cache', keyed per window (per FRAME
for a tab-bar line, which is drawn once for the frame but rendered with
whichever window is selected).  Compared with `equal' on the built DOM rather
than a hash of the printed string: a hash collision would pin a stale bar on
screen until something else changed it.  Measured on a 3-row line with a
60-segment map row: 0.151 -> 0.103 ms per render, *32% off*, with the `equal'
on two distinct-but-equal DOMs costing 0.0062 ms.  `svg-line--store-placements'
and `svg-line--interactive' stay outside the short-circuit.  66/66 package
tests pass.  NOTE the remaining cost is now `svg-line--build-lines' itself
(0.106 of the 0.103-0.151 ms), which no cache at this level can skip -- the
next lever is the segment functions, i.e. items 6, 8 and 14-16.*

* Method, and what this audit did not do

Produced by five parallel read-only audits (build, startup, redisplay,
runtime/GC, editing latency), each reporting file:line evidence, with the
load-bearing claims re-verified independently against the live =src= daemon
before being written down here.

Three claims were checked and *overturned* in the process; they are recorded
in place rather than quietly dropped, because each one would otherwise have
sent someone down a wrong path:

- Native compilation is *not* the source of the freezing -- the question that
  started this.  Zero comp subprocesses were running and no =.eln= had been
  written in two hours.
- =.eln= dylibs account for ~103 MB resident, *not* the ~600 MB an early
  reading of =__TEXT= suggested.  AOT is not a memory lever.
- librsvg rasterisation is roughly a quarter of the idle redisplay cost, not
  the bulk; the elisp rebuild dominates.  This changes the fix from image
  caching to renderer memoisation.

*Known gaps.*  85% of the 9.169 s init time is unattributed; the eager
=use-package= list covers ~130 of 145 blocks; the cost of =org-fragtog= and of
the =elpaca-wait= barriers was never measured; and the practical consequence of
the TLS bug in [[file:TODO.org][TODO.org]] is not established.  Each is flagged at its item.

*One side effect to be aware of:* while benchmarking header-line segments, an
auditor evaluated =(goto-char (point-max))= in the =FONTS.org= buffer, which is
live in a window -- point there was moved to end of buffer.  No file was
written and nothing else was changed.
