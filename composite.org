* Start here

** The rule for "worthwhile"

productivity.org ranks by =(bookkeeping removed per occurrence) x
(occurrences per week) / (build size)=, ties broken by dependency.  This
plan keeps that rule and adds one more: *a gap that a built mechanism
now makes cheap moves up*.  Three did:

- G12 the intake gate was an advice that re-ran the day packer per day
  up to a date.  =org-queue-core-horizon= is exactly that loop; G12 is
  now a fifty-line command over it.
- G2 close-the-day wanted a PROG sweep with one key per entry.
  =org-queue-apply-actions= is the sweep's writer, with its log and undo.
- G6 the routine template was to *set* capacity.  It now *derives*
  =org-queue-buckets= and =(todo) routine.org=, both of which exist and
  are typed by hand.

And one got harder to justify than the assay thought: G11 backpressure
is built, so its rank-15 slot is free, and Stage 6's "spreading a long
task before its deadline" is already a =,-o-p= away.

** What every wave shares

- *Shape.*  A pure core in =source/zettapkg/= with batch ERT tests, an Org
  harvest, a thin command file; the org-queue pattern.  New packages:
  =org-routine= (wave 1), =org-decorate= (wave 3), =org-chain= (wave 4).
  Everything else is a file inside org-queue or a module under
  =modules/org/=.
- *Buffers.*  Every new report reuses =org-queue-mode='s drawing: the
  header face ladder, =org-queue--insert-task=, the columns and their
  toggles, =RET=/=o= to jump, the write keys where they make sense.  A
  ritual is a buffer with keys, never a prompt.
- *Writes.*  Every write goes through =org-queue-apply-actions=, so it is
  all-or-none, logged, and undone by =,-o-u=.  New action kinds are added
  to =org-queue-apply--perform= with their reverse: =property= (set or
  remove one property), =tag= (add or remove one tag), =refile=.
- *The gate.*  After a week on each wave: would going back be a relief?
  If yes, the wave is reverted before the next begins (3.5's rule).

* Wave 1 — The day's frame  (G6, G2, G8, G9, G13d)

The routine read by code, the day closed by a key, projects that say

** G6 The routine as a machine-readable template  (size S)

Mechanism per productivity.org.  What changes now:

- =org-routine-core.el= (pure) parses a named table in
  =~/kb/notes/schedule.org= (=#+NAME: routine=; the existing table gains a
  =kind= column: =fixed focus dip admin off=, and an optional =days=
  column) plus a =#+NAME: variants= table.  It answers four questions:
  blocks for a weekday, the dip window, the fixed rows, and the kick /
  review / quiet windows for G16.
- *It writes the two tables the queue reads today.*  =org-queue-buckets=
  is derived: every =focus= minute is =work=, =admin= minutes are
  =housekeeping= (or whatever the row's =bucket= column says), and the
  =default= bucket is what is left.  The =setq= in
  =modules/org/org-queue.el= becomes a fallback used only when the table is
  absent.  Fixed rows with a =habit= column generate =(todo) routine.org=
  entries (Part 2 of scheduling.org said this would happen; it does here).
  Generated, never hand-edited: a =#+GENERATED= line at the top and a
  check that refuses to overwrite a file without it.
- Sub-day placement (scheduling.org step 7) is unblocked by this wave and
  stays in scheduling.org.

Tests: the five in the assay, plus: the derived bucket table for Monday
equals focus 480 / admin 120 / default the rest; a table without a
=kind= column fails with its line; the generated routine file round-trips
through the harvest as five habits with the right =HABIT_DAYS=.

Depends on Part 6 question 1 (the pomodoro window); default assumed.

** G2 Close the day  (size S)

Mechanism per productivity.org, in =org-queue-close.el= inside org-queue.
What changes now:

- The core takes today's plan (history), the harvest, the intervals, and
  *tomorrow's day plan from the horizon* (one call, honest capacity from
  G6).  Sections: Unfinished (carried, with count), Done today, Overdue
  and due tomorrow, Tomorrow's routine and fixed events, Inbox count,
  Tomorrow's draft, and (after wave 4) each chain with or without its
  next prompt.
- =N= on a draft line is =org-queue-mark-next= already; the third =N= is
  refused with the rule (=org-queue-pick-limit= 3, counted over
  tomorrow's NEXT entries).
- The PROG sweep is a list of =state= actions built for
  =org-queue-apply-actions=: one key per line to move an entry to =TODO=
  or =WAIT=, applied together, undone together.
- Writes a =:closed= stamp into the history entry for today; the morning
  report reads it and says "yesterday was closed" or not, which is R12
  made visible without a nag.
- The phrase is printed.

Tests: the eight in the assay.  =,-o-x=.

** G1 AI decoration of the inbox  (size M)

Mechanism per productivity.org 3.2 and the contract in 3.6, in a new
zettapkg =org-decorate= (=-core=, =-harvest=, =.el=).  The core takes an
entry plist, the closed lists, the calibration table and a function
that answers a prompt, and returns a proposal plist; the harvest
collects the lists from the config and neighbours from irs; the command
file runs =gptel-request= with =:schema=, writes =AI_*= properties, and
gives the Inbox view its third group and three keys: accept, edit,
reject.

What changes now:

- *Accept is an apply.*  Accepting writes the real fields through
  =org-queue-apply-actions= (new kinds =property=, =tag=, =refile=, plus the
  existing =state= and =schedule=) and strips the =AI_*= properties in the
  same transaction; reject strips only.  Undo works.
- *Effort comes from the queue's calibration* for the proposed category,
  as the assay says; the table is =org-queue-core-calibration= over the
  harvest.
- *Dates are resolved in elisp*: the model returns a phrase, =org-read-date=
  parses it against =:CREATED:=.
- =AI_KIND: delegate= and =AI_REPO= feed wave 4's kick.
- Which model: Part 6 question 4.  Default: the local model through
  gptel (qwen2.5:7b via Ollama, already installed for the router), with
  a preset switch to Claude for an inbox you choose to send.

Tests: the six in the assay, all with a stubbed model, in batch.
=,-o-f= decorates the inbox on demand; the idle timer is off until the
first week says the proposals are worth having.

** G16 The agent chain  (size M)

Mechanism per productivity.org, in a new zettapkg =org-chain=:

- The =AGENT(a!)= state after =PROG=; =org-gantt-machine-states= so its
  intervals are machine minutes in their own lane.
- =,-o-i= kicks: refuses without a prompt or past =org-queue-chain-limit=
  (3; =C-u= overrides and logs); writes =:AGENT_SESSION:=; opens the
  terminal with =claude --session-id UUID "<prompt>"=; transitions to
  =AGENT=.  =C-u C-u= is headless for =:KICK_AT:= runs, never the default.
- Landing: the Claude Code =Stop= and =Notification= hooks append plists
  to =.data/org/agent-landings.el=; Emacs watches the file and
  =zetta-org-agent-land= transitions =AGENT= to =NEXT= or =QUES= through
  the apply layer.  No elisp is evaluated from a hook.
- Views: "Landed -- review", "In flight", "Agent asks" in the Day view;
  =,-o-v a= the Chains view.
- The queue: =AGENT= excluded with reason =in-flight=; a landed entry is
  a commitment at =org-queue-review-share= (0.5) of its effort; the
  morning report's line on expected landings and review minutes.
- G2's close lists each chain with or without its next prompt.

What changes now: state changes are apply actions; the landing reader
is idempotent by session and event; the horizon treats =AGENT= like
=WAIT= (excluded, no capacity).  The hooks themselves are a
=settings.json= change (the =update-config= skill's territory), written
so the hook only appends a line.

Tests: the eight in the assay; the landing reader over a fixture log.
Decisions: Part 6 questions 12-14, defaults stated there.
