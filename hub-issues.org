* Keyboard through Blink -> mosh -> tmux -> Emacs (reference, [2026-09-11])

Why C-,, C-TAB, C-S-a/d/s/w (windmove), C-backspace and the s- keys
do not arrive, and which bindings do.  Measured where it says so;
the rest is read from the four layers' code and docs.

** How a key travels

1. /Blink/ (iPadOS).  iPadOS takes its own Cmd shortcuts first
   (Cmd-Tab, Cmd-Space, Cmd-H, screenshots...), then Blink's own
   shortcuts (configurable), then the terminal emulator encodes the
   rest.  Blink's Modifiers panel can make Caps/Cmd/Opt act as Ctrl,
   Alt (Meta) or Esc; nothing can act as Super.  Blink's "Custom
   presses" panel maps one physical chord to an arbitrary byte
   sequence (hex/ASCII; blinksh/blink#1015, shipped 13.5; modifier
   chords in custom presses broke once, fixed in v15, #1335).
2. /mosh/.  Input is a transparent byte stream: whatever Blink emits
   reaches the server.  OUTPUT is not: mosh-server runs its own
   terminal emulator and re-synthesises the screen for the client, so
   any escape an application sends to the TERMINAL is dropped on the
   floor -- the modifyOtherKeys enable (=CSI > 4;1 m=), the CSI u
   push, DECSCUSR, OSC 52.  (mosh-devel: "How to support xterm
   modifier key setting", unanswered; the cursor-style PR #1355 is
   the same wall.)  mosh also eats C-^ (its escape key).
3. /tmux 3.4/ (=extended-keys on=).  Swallows the prefix C-b.
   Decodes both extended-key encodings coming IN from the client and
   re-encodes for panes that asked for them (Emacs asks at frame init:
   =xterm-tmux-extra-capabilities= carries =modifyOtherKeys=, so
   term/tmux.el sends the request; tmux records the pane's wish, then
   forwards the request outward, where mosh drops it).  Standard
   sequences (CSI arrows with modifiers, function keys, backtab) pass
   through untouched.
4. /Emacs tty/ (term/tmux.el -> term/xterm.el).  Decodes the standard
   xterm sequences and a FIXED table of extended keys in both forms
   (=ESC [27;MOD;CODE~= and =ESC [CODE;MOD u=, xterm.el lines 520-642
   in 31.1): C-tab, C-S-tab, C-return, S-return, S-tab, C-, C-. C-;
   C-' C-= C-/ C-- C-\ C-digits, C-M- of the same, and the C-S-
   punctuation.  NOT in the table: C-S-<letter> (C-S-a...), C-<letter>
   variants, C-backspace (=27;5;127~=).  Those need an
   =input-decode-map= entry of our own.

** Recommendation: bindings to adopt so the same config works headless

- /Insert-state leader/: C-, stays for the GUI; add =M-,= as the
  universal twin (ESC , ; free in evil insert and in the minibuffer;
  org's =C-c ,= is unrelated).  Normal-state =,= already works.
- /windmove/: C-S-a/d/s/w have no tty form at all.  Adopt
  =C-M-<arrows>= (standard CSI, modifier 7; free in org, which uses
  M-<arrows> and M-S-<arrows> for structure editing and S-<arrows>
  for timestamps/shift-select).  Keep the WASD chords on the GUI if
  wanted; the arrows are the universal set.
- /Tab-line next/prev/: C-tab / C-S-tab need injection.  Adopt evil
  normal-state =g t= / =g T= (vim's tab convention, free in evil) or
  =M-n= / =M-p= where a mode leaves them free; the g1-g9 jumps already
  cover direct selection once the tab-line split ships.
- /C-backspace/: use =M-DEL= or, in insert state, evil's =C-w=.
- /C-S-<letter>/ in general (C-S-t org-babel-tangle, C-S-r in the
  minibuffer, C-S-d delete-other-windows, C-S-j/k pdf paging): each
  becomes a =M-<uppercase>= twin (=M-T=, =M-R=, =M-D=) or moves under
  the =,= map.  M-uppercase is ESC + the shifted char and always
  arrives.
- /s- bindings/ (118): no universal twin exists.  Triage into the =,=
  launch map (already the modal leader) for the ones wanted on the
  hub; the rest stay GUI-only.  Do not map Cmd to Alt wholesale: the
  s- set would land on top of the existing M- set.
- Avoid on any tty: =M-[= (CSI), =M-O=, C-b/C-h/C-^, and any binding
  that distinguishes C-i from TAB, C-m from RET, C-[ from ESC.

** The real Super key in headless (research, [2026-09-11])

Goal: press the same Cmd chords in GUI and headless.  Three cases.

*** Blink (iPad), mosh or ssh: Cmd as the "8-bit" modifier role

Blink's Modifiers panel offers six roles per modifier key: None,
8-bit, Escape, Shift, Control, Meta (=KB/Native/Model/KeyModifier.swift=).
Read from the bundled hterm (=Resources/hterm_all.min.js=):

- /8-bit/ ("Add 128 to the unshifted character as in xterm") is an
  Alt-role with =altSendsWhat="8-bit"=: for a one-character key the
  chord sends =String.fromCharCode(code + 128)= -- a JS character, so
  the transport UTF-8-encodes it.  Cmd-b becomes U+00E2 "â" (bytes C3
  A2), Cmd-B (shift) U+00C2 "Â", Cmd-1 U+00B1, Cmd-, U+00AC.  Mosh
  passes input bytes untouched, tmux passes UTF-8, Emacs's keyboard
  coding is utf-8: the key arrives as ONE character event, no
  negotiation, no lead-byte stall.
- /Escape/ is the same Alt-role with =altSendsWhat="escape"= (ESC
  prefix: Emacs Meta).  The flag is a single field, BUT =_mod()= is
  re-evaluated on every modifier keydown/keyup from that key's own
  configured role, so Option=Escape and Cmd=8-bit coexist: the flag
  follows the modifier currently held.  (Holding both at once is the
  one ambiguous case.)
- /Meta/ (=metaSendsEscape=false=) only adds the modifier parameter to
  control sequences: Cmd-<arrow> would come as =CSI 1;9A=.  For
  letters it sends nothing useful.  The JS also knows a "Meta-Escape"
  role the Swift picker does not expose.
- Not covered by 8-bit: Cmd with arrows, F-keys, Tab, Return
  (multi-character sequences skip the +128 path).  Those few can be
  Custom presses, or the "Meta" role on the OTHER Cmd key plus decode
  entries for modifier 9.

Emacs side, headless template, tty-only: one =input-decode-map= loop
mapping each Latin-1 character U+00A1..U+00FE back to =[s-<char>]=
(uppercase keeps its case, so Cmd-Shift-b is =s-B=, as in the GUI).
Every existing =s-= binding then works unchanged.  Cost: those Latin-1
characters cannot be TYPED on the hub while the map is active (é is
s-i, ñ is s-q, ü is s-u, ç is s-g); limit the loop to the characters
the config actually binds if that matters, or keep a toggle.  To
verify: whether bracketed paste of Latin-1 text goes through
=input-decode-map= (xterm-paste reads the pasted characters itself; if
it does not, pasting is unaffected).

Chords iPadOS keeps for itself never reach Blink: Cmd-Tab, Cmd-Space,
Cmd-H, Cmd-Shift-3/4/5, Cmd-Option-D, Globe combinations.  Blink's own
Cmd shortcuts (Cmd-T/W/N/O/K, Cmd-digits, Cmd-[ ], font size) are all
reassignable in Blink Shortcuts.

Verify with Blink's built-in =showkey= (prints each byte): Cmd-b should
print 0xC3 0xA2; then in Emacs =C-h k Cmd-b= should say =s-b=.

*** Mac terminal, local or ssh (Ghostty, kitty, WezTerm, iTerm2 3.5+): kitty keyboard protocol

Emacs 31 has no native support (checked NEWS); the =kkp= package
(MELPA) enables the protocol from =tty-setup-hook= where the terminal
answers the capability query, and decodes super/hyper natively, so the
physical Cmd key arrives as =s-= with no per-key work.  Terminal.app
does not speak it.  Two conditions: the terminal must not consume the
chord itself (Ghostty binds Cmd-C/V/N/T/W/Q/digits/+/-/0 by default;
=keybind = cmd+b=unbind= per key in its config, or use its
=text:= binding to inject), and tmux in the path must relay the
protocol -- tmux 3.4 relays the CSI u form, the kitty flags only
partly, so ssh-into-tmux needs a test; a plain ssh session without
tmux is clean.  macOS keeps Cmd-Tab, Cmd-Space, Cmd-H/M/Q.

The Blink 8-bit trick also works from a Mac terminal that can send
text for a chord (Ghostty =text:=, kitty =send_text=), but per key,
so kkp is the generic answer there.

*** Any terminal, last resort: the built-in modifier prefix

=C-x @ s <key>= is =s-<key>= on every tty (=event-apply-super-modifier=
in =function-key-map=; =C-x @ c= for control, =C-x @ S= shift).  Bind a
shorter prefix in the headless template.  Two keystrokes, zero
terminal cooperation, always available.

** DONE TAB in evil normal state runs evil-jump-forward, not org-cycle

:SEEN: [2026-09-11] hub daemon, ~/kb/inbox.org in normal state: =(key-binding (kbd "TAB"))= is =evil-jump-forward=, =(key-binding [tab])= is =org-cycle=

Not a broken evil config; a terminal fact.  On a tty the Tab key and
C-i are the same byte (0x09): there is no separate =<tab>= event, the
way there is in a GUI frame.  Evil binds C-i to =evil-jump-forward= in
=evil-motion-state-map= (=evil-want-C-i-jump= is t, the default; the
config never sets it), and a state map outranks =org-mode-map=, so the
byte lands on the jump.  In a GUI frame Tab arrives as =<tab>=, a
different event from =C-i=, org's binding is found first, and the
same config behaves.  Measured: =org-mode-map= has TAB -> =org-cycle=,
the motion map has C-i -> =evil-jump-forward=, and the tty lookup
picks the latter.

Nothing in the tmux/Blink chain can separate them: even with
=modifyOtherKeys= on, xterm.el decodes a modified C-i back to the
character 9.

Fix: in the headless template, before evil loads (the template is
read first), =(setq evil-want-C-i-jump nil)= -- evil then leaves C-i
alone and Tab falls through to the major mode everywhere.  Give the
jump another key on the hub so the C-o / C-i pair survives, e.g.
=g ,= or =C-M-o= in the motion map.  Alternative with the same effect
and no template change: unbind C-i in =evil-motion-state-map= from
=tty-setup-hook=, but that map is global, so a mixed GUI+tty daemon
would lose it on both; the hub is tty-only, so either works, the
template setting is the smaller one.

Same family, worth checking while there: C-m is RET and C-[ is ESC on
a tty.  Evil handles ESC itself (=evil-esc-mode=, with
=evil-esc-delay= for the Alt-as-ESC ambiguity); RET is not rebound by
evil.  Any =C-m= / =C-i= / =C-[= binding elsewhere in the config
collides the same way on the hub.
