* Start here

** Verdict [2026-09-10]

*Feasible, and no paid upgrade is needed.*  The config already loads on
headless Linux under Emacs 29: every pull request runs the entire module set
in batch on ubuntu-latest (see Part 2).  What the hub changes is two things
CI never exercises: its Emacs has no SVG support, and the machine has no
compiler toolchain.  [phase 2] CI's own gate also has a hole: it discards
use-package's error reports, so a =:config= that fails on 29.x is green
today (Part 2, item 3).

The work is:
- a headless module profile in .zetta.d (a module list plus a populated
  =zetta-module-conditions=),
- roughly eight small guards in individual modules (Part 3),
- an apt list in the existing hub bootstrap script (Part 5),
- one unattended cold build on the hub (Part 4),
- [phase 2] a committed =templates/zetta.headless.el= plus a hand-placed
  hub private file, since neither user file is in .files (Part 5),
- [phase 2] an =emacs-nox= CI row that also fails on use-package errors
  (Phase B),
- [phase 2] a build entry point with a multi-hour window: =bin/zetta
  install= gives up after ten minutes (Part 4).

The dotfiles need a Linux path only for the slice actually wanted on a
server.  Do not port =bootstrap.sh=.

** Deviations from the plan, with reasons

- *=auth-sources= could not be set from the template alone.*  =init.el=
  loads =~/.zetta.el= at line 18 and set =auth-sources= to =(zetta-op)=
  unconditionally at line 103, so the template's =nil= was clobbered
  and Part 7's "the private file can be a one-line =;;=" did not hold.
  Fix in =init.el=: the 1Password backend is installed only when the
  =op= binary exists.  On the Mac nothing changes; on the hub the
  template's value survives.
- *=emacs.service= carries =ConditionPathExists=%h/.zetta.d/elpaca/builds=.*
  The plan's ordering (units in step 2, cold build in step 3) leaves a
  window where a reboot would start an unbuilt zetta, which would clone
  and build inside the daemon, hit the start timeout and loop under
  =Restart=on-failure= on one core.  With the condition the unit is
  skipped, not failed, and =emacs-lean= is the editor until the build
  exists.  Cost: after a deploy and before the build, =e= fails and the
  owner starts =emacs-lean= by hand.
- *=TimeoutStartSec=900= is provisional*, per Part 4: the real value
  is twice a measured =emacs-init-time= after the cold build.  Recorded
  as such in the unit and the README.
- *Phase A was applied over ssh, not through =hub-deploy=.*  A deploy
  ships the whole of =hub/=, including the Phase D units, and those
  must not go live before the config is on =main= and built.  The apt
  and timezone commands are idempotent and identical to what the
  bootstrap now runs, so the next deploy is a no-op for them.
- *The local batch rehearsal needed an overlay.*  On the Mac,
  =bin/zetta ci-test= fails in the bootstrap before any module loads:
  the =source/bootstrap/*.elc= on disk expand =use-package= forms in a
  way that works on the daemon path (queues processed at after-init;
  the live daemon started 2026-09-09 on bytecode from 09-06) but not in
  batch, where =-l init.el= runs after after-init.  CI never sees this
  (fresh checkouts have no source =.elc=), and neither will the hub's
  daemon.  The rehearsal therefore ran against an =.elc=-free copy of
  the config sharing the real elpaca builds by symlink, with the SVG
  predicate and =image-type-available-p= forced nil to imitate
  emacs-nox.  Outcome: see "Rehearsal" below.

Three things the first start found that neither CI nor the rehearsal
could (all deferred or per-machine, Part 2 item 4), each fixed:

- *Module file name versus library name.*  hyperbole's autoloads carry
  =(eval-after-load "ibuffer" '(define-key ibuffer-mode-map ...))=, and
  =eval-after-load= matches load-history by FILE name, which
  =modules/core/ibuffer.el= satisfies the moment it loads.  On the GUI
  profile all-the-icons-ibuffer had already loaded the real ibuffer; on
  the hub it was still deferred behind =:commands=, so hyperbole's
  =:defer 1= require died with void-variable =ibuffer-mode-map= and
  hyperbole was simply absent.  Fix: =core/ibuffer.el= is =:demand t=.
  The same trap waits for any module file named after a library that
  something else =eval-after-load=s.
- *A synced per-machine cache.*  =~/kb/wiki/.hywiki.eld= records
  =hywiki-directory= as an absolute path.  A copy that reached the hub
  in July, before the ignore rule, set the directory to
  =/Users/charlieholland/kb/wiki/= on the hub, and hyperbole's config
  died trying to create it.  The rule exists in =.stignore-shared=;
  the stale file was deleted on the hub by hand.  Nothing in
  =modules/= carries a =/Users= path; the audit's claim holds.
- *Grammar ABI.*  tree-sitter-python v0.24+ emits ABI 15; Emacs 29
  reads up to 14 ("version-mismatch: 15").  Pinned to v0.23.6 in
  =lang/treesit.el=.

*The update flow's first run broke, and fixed a real bug.*  After
#142 merged, =git pull && bin/zetta build= on the hub died in phase 1
with "Cannot load key-chord" then void-function =general-define-key=:
the Mac rehearsal's bytecode failure (above), now on the machine it
matters for.  The first build's phase 2 had written
=source/bootstrap/*.elc=, and a batch =-l init.el= cannot start from
them.  =install= never sees it because it purges every =.elc= first;
=build= and =sync= did not.  Both now purge module and bootstrap
bytecode before phase 1 (eln-cache still kept), which is what the
first cold build had accidentally enjoyed.  Why the compiled bootstrap
only works on the daemon path is still unexplained; the purge sidesteps
it for a few seconds of recompilation.

One thing the build revealed about =bin/zetta= itself, pre-existing and
shared with =install=: the native-compile phase runs without the
config's load-path, so most packages fail with "Cannot open load file"
inside the compile worker; 212 =.eln= files from 195 packages, 28 MB.
The Mac's 0.7 GB eln cache came from run-time deferred compilation,
never from that phase.  The hub will do the same, one worker at a
time.  Follow-up: give phase 3 =-l init.el= plus =(elpaca-wait)= so
the ahead-of-time compile actually compiles.

* Part 1 -- What already works in our favour

- *CI is the existence proof.*  =.github/workflows/ci.yml:74= runs the
  whole module set in batch on ubuntu-latest under 29.4, 30.2 and the 31
  pretest, gating on zero failed packages, zero unpinned packages, and no
  void-function or wrong-type-argument in the log (=bin/zetta ci-test=).
  Linux and Emacs 29 are already supported targets.  [phase 2] The gate
  has a hole, though: it discards use-package's own error reports (Part 2,
  item 3).

- *The loader has the right hook.*  =zetta-module-conditions= in
  =source/bootstrap/bootstrap-modules.el= is an alist of module file to
  predicate; a module loads only when its predicate is true, and is skipped
  with a message otherwise.  It is currently =nil=.  Its docstring already
  shows the intended =image-type-available-p= use and explains why guarding
  inside the file is the wrong alternative (definitions stop being
  top-level, =defsubst= stops inlining).

- *The user config can branch.*  =init.el:18= loads =~/.zetta.el= with
  =load-file=, so it can pick a module set by hostname or an environment
  variable.  =zetta-modules!= just setqs =user-files=; if it is never
  called the hardcoded list in =source/init-data/init-data.el= wins, so a
  headless branch must still call it.  Parser gotcha
  (=bootstrap-modules.el:227=): a category spec switches to exclusion mode
  if any symbol starts with a hyphen and then silently ignores plain
  includes, so one list cannot mix the two.  [phase 2] Two more facts about
  the user files: neither =~/.zetta.el= nor =~/.private.el= is in .files
  (both are plain files in =$HOME= on the Mac, and the hub has neither),
  and =bin/zetta install= copies the full-profile
  =templates/zetta.example.el= into place when =~/.zetta.el= is missing.
  So the headless template has to be installed before the first build,
  not after.  On the other side of the ledger, =zetta--module-files= lists
  what is on disk, so a module the hub's checkout lacks is simply absent,
  not an error.

- *The bootstrap is TTY-safe.*  Nothing in =source/bootstrap/=, =init.el=
  or =early-init.el= requires a GUI or macOS.  =bootstrap-brushup.el:38=
  wraps its face overrides in =(when window-system)= and ships a palette
  fallback at lines 15-33.  =bootstrap-repeatable.el:8= gates on 30.1.
  =early-init.el:40= already special-cases daemon startup.  The =:brushup=
  keyword is registered by the external brushup package, not this repo
  (=bootstrap-use-package-keywords.el:35=), and brushup is bootstrap-level,
  so excluding =:ui= does not strand the ~20 modules that use it.

- *Secrets are skippable.*  =zetta-op-load= is called from
  =~/.private.el:30= only, never from =init.el=.  =init.el:106= loads
  =~/.private.el= unguarded, so the hub needs its own private file; the
  current one is 548 lines, mostly mu4e/msmtp with =/opt/homebrew= paths
  (lines 127, 133, 137, 297), none of which belongs on the hub.

- *The SVG engine is inert without its consumers.*  =modules/core/line-utils.el=
  holds the ~2,100-line mode-line and tab-bar engine in the *core*
  category.  Its =svg-line= calls are =fboundp=-guarded at 165, 226, 2123
  and bare at 1007, 1945, 2010, 2031 -- but the bare ones sit in functions
  only =ui/telephone-line.el= and =ui/disabled/line.el= call.  Excluding the
  UI files leaves it loaded and harmless.  =core/interface.el:688= reads
  =zetta-svg-line-font= through =bound-and-true-p=.

- *The hub already has a Linux installer.*  =~/.files/hub/bootstrap-hub.sh=
  (105 lines) is idempotent and apt-based, and is what =hub-deploy= runs
  after an =scp= of =hub/= to =~/syncthing-hub/=.  It is the natural place
  for build dependencies.

* Part 2 -- What CI does not prove

CI runs on GitHub's ubuntu-latest image with a =setup-emacs= build that has
librsvg and a full toolchain, so vterm and pdf-tools build there and every
SVG module loads.  The hub differs in exactly those two respects:

1. =emacs-nox= 29.3: =(image-type-available-p 'svg)= is nil.
2. No gcc/make/cmake, no libvterm, no poppler, no tree-sitter CLI.

Both vterm and pdf-tools are in =elpaca-lock.el=, which is why CI builds
them and the hub will not.  Everything in Part 3 follows from these two
facts plus macOS-isms that CI's Linux run already tolerates silently.

[phase 2] Two more things CI does not prove, found by reading the harness:

3. *The error gate is porous.*  =bin/zetta ci-test= greps the log for
   void-function, wrong-type-argument and debug-early, then drops every
   line containing "use-package" (=bin/zetta:704=; the local =test= command
   has the same filter at line 421).  use-package wraps each =:config= in
   a condition-case and reports failures as "Error (use-package): ..."
   warnings, which is exactly what that filter discards.  So a =:config=
   that signals on 29.x passes CI today: =ui/ef-themes.el:11= fails on
   29.4 in every PR run and nobody sees it.  The headless row in Phase B
   must fail on those warnings too, or none of the Part 3 guards is
   CI-verifiable.  Measured blast radius of tightening it: the last cold
   run (34091453070, 2026-09-07) hides, per row, ef-themes, modern-fringes
   and gptel on 29.4 and 30.2; modern-fringes and gptel on 31; and
   treesit-tap on 29.4 alone.  Four packages, each a few-line fix (Phase B,
   step 3); treesit-tap is a hub break the first audit missed (Part 3).
4. *Deferred =:config= never runs in batch.*  A =use-package= with =:hook=,
   =:commands=, =:mode= or =:bind= defers its =:config= to first use, and
   =use-package-always-defer= is not set, so CI exercises the eager forms
   only (29 =:demand t=, 4 =:defer t=, the rest decided per keyword).
   Breaks behind a deferred form surface on the hub at first use, which
   is why Phase C's tests are manual.  The batch-versus-daemon worry, by
   contrast, is small: the only =noninteractive= gate in =modules/= is
   vterm's, and the only =daemonp= is =early-init.el:40=.

ahead-of-time compile once during provisioning.  A 2 OCPU resize makes the
daemon usable while that runs.

* Part 7 -- Open questions for phase 2

- *Profile mechanism*: hostname branch in =~/.zetta.el=, an environment
  variable, or a committed =templates/zetta.headless.el= that the hub
  bootstrap installs?  The last is the most reproducible and keeps CI able
  to test it.  [phase 2] Settled: the template.  Neither user file is in
  .files, and =bin/zetta install= writes the full-profile example when
  =~/.zetta.el= is missing, so a committed template installed by the
  bootstrap is required, not merely preferable.
- *Predicate versus exclusion*: which skips belong in
  =zetta-module-conditions= (capability-based, self-correcting if the hub
  ever gets an SVG build) and which in the profile's exclusion list
  (taste-based)?  [phase 2] Settled: the SVG-chrome files go in the
  =zetta-module-conditions= default in bootstrap-modules.el, everything
  else in the template's lists (Phase B, steps 1 and 2).
- *Emacs version on the hub*: stay on apt 29.3, or build 31 from source
  with =.files/install_emacs_source.sh= adapted for Linux?  Emacs 31 has
  TTY child frames, which makes corfu and posframe work unchanged, and
  matches the Mac's bytecode expectations.  Costs a long compile on the hub
  and a second moving pretest to track.  [phase 2] One more cost of 31:
  apt 29.3 is also what ubuntu-latest ships, which is what makes a
  bit-identical CI row possible (Phase B).  A source-built 31 on the hub
  forfeits that unless CI builds the same.  Default: stay on 29.3; revisit
  only if Phase C finds corfu-terminal inadequate.
- *Secrets*: install =op= with the service-account token from
  =~/.zshenv.local=, or keep the hub secret-free and let elfeed, mastodon,
  forge and gptel stay unconfigured there?  [phase 2] Either way the hub
  private file must set =auth-sources=: =init.el:103= points it at the
  1Password backend unconditionally, so with no =op= every credential
  lookup silently returns nothing.  Default: secret-free, =auth-sources=
  nil in the template, and the secret-bearing modules simply absent from
  the inclusion lists.  Owner's call to reverse.
- *What the hub Emacs is for*: org editing, agenda, capture and search over
  =~/kb= is the stated use.  Whether magit, lsp, ai.el and the app modules
  belong on it at all decides how much of the exclusion list is "cannot"
  versus "should not".  [phase 2] Resolved by shape rather than by list:
  =:tools= and =:app= are inclusion lists seeded from the stated use, so
  nothing reaches the hub without being asked for (Phase B, step 2).
- *Fallback*: keep the lean init reachable as a second daemon unit, or as a
  chemacs profile like the Mac?  [phase 2] If a second unit: distinct
  socket names, see Part 5.
