* The one-paragraph version

Work lives in the =(todo)= org files.  A task is an org heading with a TODO
state, an optional =:Effort:=, and optional SCHEDULED / DEADLINE / priority.
=,-o-Q= reads those files, packs one day out of them against the minutes
each *bucket* of the day has (work, reading, housekeeping...) after the
day's *habits* are reserved, and draws the result as a report.  The report
writes nothing.  You change what gets planned by editing the entries --
state, SCHEDULED, DEADLINE, priority -- and pressing =g=; or by pressing one
of five keys on a line, which writes that one decision to the entry; or by
asking for a *proposal* over a week or a month, accepting the lines you
agree with, and applying them.  Everything the machine writes carries a
=:PLACED:= stamp, so it stays distinguishable from what you wrote, can be
moved by a later proposal, and can be undone.

Around the plan sit the *rituals*: buffers with keys, never prompts, each
run on a cadence and each deriving what it shows from the files rather
than asking you to type it.  You close the day with a key, review the
week from one generated pack, let a model propose how to file each
inbox capture and accept with a key, hand a task to an agent and get it
back as a landing, and set a theme and three missions a season.  The
capacity every plan packs against comes from the routine table in
=schedule.org=; time comes from TODO state transitions, never org-clock.
Every write any of it makes to a task entry goes through one apply
layer, is logged, and is undone by =,-o-u=.  Three things write files
outside it: a journal line, a promoted page, and the mail stub.

* States

Defined in =modules/org/org.el=.

| state | key | meaning                                                  | queue behaviour                                     |
|-------+-----+----------------------------------------------------------+-----------------------------------------------------|
| TODO  | =t= | open work                                                | scored candidate                                    |
| NEXT  | =N= | you have decided this is next, whatever the formula says | *commitment*, never scored                          |
| PROG  | =p= | in progress; entering it starts the derived clock        | scored, with a "finishing" bonus; at most 3 per day |
| AGENT | =a= | an agent has the ball: a chain in flight                 | excluded, reason =in-flight=; never human capacity  |
| WAIT  | =w= | waiting on someone; asks for a note                      | excluded unless a deadline is within 7 days         |
| QUES  | =q= | an open question; asks for a note                        | scored, docked 1.5                                  |
| HOLD  | =h= | paused by choice; asks for a note                        | excluded                                            |
| IDEA  | =i= | someday / maybe                                          | excluded                                            |
| DONE  | =d= | finished                                                 | excluded; feeds calibration                         |
| NOPE  | =n= | abandoned; asks for a note                               | excluded; feeds calibration                         |

Change a state with =C-c C-t= on the heading, then the state's key.  The
states you leave work in (WAIT, QUES, HOLD, NOPE) prompt for a one-line
note; PROG and DONE do not.  There is no =,-o-t= for this yet: the key is
bound to the Logseq todo search (=org-capture.el= loads after =org.el= and
rebinds it), and the command =org.el= meant for it calls =zetta-org-todo=,
which is defined nowhere.

The five write keys are the only writes this buffer makes.  Each is one
decision on one line, applied at once, saved, logged, and undoable with
=,-o-u=.

The close, the day log, the pack, the season and the horizon buffers are
all drawn in this mode: the same columns, =RET=, =o=, =n=/=p= and the column
toggles work in every one of them, and each adds its own keys, listed in
its section.

* The planner, step by step

** What one run does

1. Harvests every TODO-state heading in =org-agenda-files= with org-ql.
   Each becomes a plist: state, effort, dates, priority, tags, category,
   impact, blockers, habit flags, the =:PLACED:= stamp, and the minutes the
   derived clock has measured.
2. Marks tasks that were on the previous plan and are still open as
   carried.  This is kept in =.data/org/queue-history.el= as a list of IDs.
3. Filters.  Done, HOLD, IDEA, blocked, waiting-with-no-near-deadline,
   wrong context or energy, habits, and appointments on other days are
   excluded, each with a named reason.  Tasks scheduled after today are
   deferred.
4. Builds the day's buckets.  Each bucket's minutes for this weekday,
   less the habits that fall on it, less slack, is what it can hold.
5. Stamps every hard-deadline task with its *start-by* day.
6. Admits commitments, unscored and in date order: scheduled ON today,
   deadline today or earlier, a plain active timestamp today, NEXT, or
   start-by reached.  If these overflow a bucket, that bucket says
   OVERCOMMITTED and nothing more is planned in it; the other buckets
   still fill.
7. Fills each bucket from its candidates, highest score first, holding at
   most =org-queue-wip-limit= (3) PROG items across the day.  A bucket
   with =:spill t= hands what it did not use to =default=.
8. If a bucket still has room, pulls deferred work in it forward.
9. Draws it.  Every harvested task lands in exactly one of planned, cut,
   deferred or excluded, with a reason you can read.

** Granularity

- One day per run.  Plain =,-o-Q= is today; =C-u ,-o-Q= asks for a day.
  Longer ranges are the horizon and the proposal, below.
- Whole tasks, in minutes.  The day packer never splits a task; the
  horizon does (slices), and only for commitments.
- Capacity is per bucket per weekday, *derived from the routine table*
  (see "The routine table, read by code"): focus and dip minutes are
  =work=, admin minutes are =housekeeping=, each habit row reserves its
  bucket, =default= is a fixed floor.  Which tags and categories each
  bucket claims is =org-routine-bucket-matches=:

  | bucket       | claims                                   |
  |--------------+------------------------------------------|
  | work         | categories work, emacs, cal              |
  | reading      | tag reading, category learn              |
  | body         | tag body                                 |
  | housekeeping | tag housekeeping, categories home, buy   |
  | default      | everything else                          |

  Until the real =schedule.org= has the table's columns, the fallback
  table in =modules/org/org-queue.el= is in force (work 5:00, reading
  1:00, body 2:00, housekeeping 1:00, default 1:00, flat across the
  week) and the echo area says so when the queue loads.
- A task with no =:Effort:= is planned as 30 minutes and drawn in the italic
  "guessed" face.  An estimate is encouraged, never required.
- The plan is recomputed from scratch on every =g=.

** How a candidate is scored

#+begin_example
score =  deadline * urgency(days until deadline)   convex; overdue pinned to 1
                                                    soft deadlines x0.35
       + priority * priority weight                A > B > none > C
       + impact   * (IMPACT - 3) / 2                 -1 to 1 around a neutral 3
       + age      * log(1 + days since CREATED)
       + progress * (state is PROG)                finishing beats starting
       + quick    * (effort <= 15 min)
       + carry    * (was on an earlier plan, or scheduled for a day gone by)
       + stick    * (a machine placement already on this day, while proposing)
       + mission  * (serves a mission of the season)      the priority-B weight
       - glut     * (tasks already picked from this category)
       + state weight                              QUES: -1.5
#+end_example

A stale SCHEDULED in the past is deliberately *not* a commitment.  It feeds
the carry term instead.  A past DEADLINE *is* a commitment, and stays one
until you move it or close the task.

*A future SCHEDULED wins over everything.*  The filter sorts a task
scheduled after today into "deferred" before the commitment check runs, so
a NEXT task or an overdue task that also carries a later SCHEDULED is
deferred, not committed.  If you mean "now", clear the schedule
(=C-u ,-o-S=) as well as setting NEXT.

** Start-by: deadlines push back

A hard DEADLINE commits a task from its *start-by* day: the latest day on
which the calibrated effort still fits into the free minutes of the days
up to and including the deadline.  Six hours due Friday with two free
hours a day has a start-by of Wednesday; on Wednesday it is a commitment,
before that a candidate.  The note reads =start by <day>, due <day>=; the
=d= column shows =by <day>=.  The deadline day counts as workable, because
an Org deadline is inclusive.  Soft deadlines (=DEADLINE_TYPE: soft=) get
none of this.

In the single-day plan a start-by commitment bigger than the day still
lands whole and the bucket says OVERCOMMITTED, which is the truth of it.
The horizon is where it gets sliced.

Under the date, before the bucket line, two more lines may appear:
"yesterday closed at 17:02" (or "was not closed"), and the chains' line

minutes of review").  The bucket line appears when there is more than
one bucket: each bucket's planned minutes of its usable, =OVER= when its

..., due ...=, =next=.  On a Chosen line it is the score.  Press TAB and
every task that lost is listed with its reason; a bucket with no minutes
today cuts with "its bucket has no minutes today".

** Reading an overcommitted report

The first real run, before the fixture was tuned, looked like this:

#+begin_example
Saturday 12 September 2026   33:16 planned of 1:12 usable (1:30 capacity, 20% slack)

OVERCOMMITTED by 32:04 -- nothing was planned on top.

Committed
    0:19  home    Cancel Hodinkee insurance before renewal  due today
    4:36  work    Prepare slides for the architecture review  overdue since 20260909
    ...
27 cut, 51 excluded, 6 deferred.  TAB to see why.
#+end_example

How to read it:

- The commitments alone exceed usable time, so the scorer never ran in
  that bucket.  Every candidate there is cut with "the day is already
  overcommitted".  With buckets, only the overflowing bucket is affected.
- Minutes are larger than the entries' =:Effort:= when calibration found
  finished work overran its estimates.  =c= shows the per-category factors.
- The tally line accounts for every entry: committed + cut + excluded +
  deferred is the whole corpus.
- The fix is triage, not tuning: move each overdue deadline (=,-o-D=), close
  what is done (=C-c C-t d=), park what you are consciously not doing (=H= on
  the line), un-NEXT what you no longer mean, then =g=.

* Buckets

A day is a few named pools, not one.  Each bucket is a *reservation and a
limit*: the packer fills it even when better-scoring work exists elsewhere,
and never past its minutes.  =housekeeping= with 30 minutes means the day
holds up to half an hour of housekeeping and will look for some.

- A task belongs to the *first* bucket whose match holds, in table order;
  =:match= can name categories, tags (any of), or a predicate.  Unclaimed
  tasks go to =default=.
- =:minutes= is one number or a per-weekday alist.  A weekday missing from
  the alist closes the bucket that day.
- =:spill t= lets a bucket's unused minutes go to =default= at the end.
  Off by default: an unfilled reading hour is a finding, not free work time.
- Overcommitment is per bucket.  A meeting-heavy day overflows =work= and
  still packs =reading=.
- With =org-queue-buckets= nil, =org-queue-capacity= is the only bucket and
  the planner behaves as it did before.

* Habits

An entry with =:STYLE: habit= is time already decided, not work to finish.
It is subtracted from its bucket before packing and listed under Routine.

#+begin_example
,* TODO Lift weights  :body:
SCHEDULED: <2026-09-12 Sat .+1d>
:PROPERTIES:
:STYLE:      habit
:Effort:     1:00
:HABIT_DAYS: Mon Tue Wed Thu Fri Sat
:END:
#+end_example

- =:HABIT_DAYS:= is the weekday set ("except Sundays"); absent means every
  day.
- =:Effort:= is the reservation.  Slack is taken after it: a five-hour
  bucket with an hour of habits has =(300 - 60) x 0.8= usable minutes.
- A repeater *without* =STYLE=habit= is still a task ("Water the plants
  +3d" queues as work).  You decide per entry.
- Ticking DONE rolls the repeater as org always did, and is the tick the
  strength score counts (see "Habits, phase 2" below).

Habits live in =(todo) routine.org=, *generated* from the routine table's
habit rows by =M-x org-routine-generate-habits= (the fixture's has lift,
bike, clean, read, laundry).  The real corpus has no such file yet; it
appears once =schedule.org= has the table's columns.

* The horizon: more than one day, read-only

=,-o-P= asks for a scope -- today, tomorrow, 3 days, week, fortnight,
month, backlog (until the pool is empty or 90 days), or until a date --
and runs the day packer across it with the pool evolving: a task planned
on one day is gone the next, deferred work arrives on its day, habits
reserve every day they fall on, and a commitment too big for its day is
*sliced* across the days before its deadline.  Nothing is written.

#+begin_example
Horizon 2026-09-12 to 2026-09-18
   7 days, 33 tasks placed, 17 unplaced, 0 deadlines missed

Sat 12 Sep 4:47 of 6:08   4 committed, 0 chosen, 0 pulled
Sun 13 Sep 5:01 of 7:20   3 committed, 1 chosen, 0 pulled
...
Never fits in 7 days (17)
Missed deadlines (0)
#+end_example

=TAB= on a day opens the full plan for it, with the same columns, notes and
keys as =*org-queue*= (including the write keys, which act on that day).
"Never fits" is what is still eligible after the last day.  "Missed
deadlines" are hard deadlines inside the range the days could not cover,
with the shortfall.

Known limit: a repeating appointment appears on one day of the range, its
first occurrence, because the harvest rolls repeaters forward once.

* Proposals: the write-back loop

=,-o-p= asks for the same scopes and turns the simulation into a list of
placements for review:

#+begin_example
Proposal 2026-09-12 to 2026-09-18
   14 to schedule, 0 to move, 0 to unschedule, 0 findings;  0 accepted (0:00), 0 rejected

Sat 12 Sep   5:05
       0:50  emacs   TODO  Make zetta-op-read lazy so startup stops blocking  -> 2026-09-12   start by 2026-09-12 for 2026-09-13
       2:22  work    TODO  Prepare slides for the architecture review  -> 2026-09-12   start by ..., first slice; 2 slices to 2026-09-13

Mon 14 Sep   0:30
       0:30  home    NEXT  Track down the old TIAA 401k  -> 2026-09-14   next
#+end_example

What it proposes, and what it never does:

- *schedule* a task that has no date, on the day the simulation placed it;
- *move* a machine placement (=:PLACED:=) the simulation now puts elsewhere;
- *unschedule* a machine placement inside the range the simulation no
  longer uses;
- never a date you wrote yourself, never a DEADLINE, never a state;
- never a SCHEDULED that a date already fixes: an appointment on its day,
  a task on its deadline day;
- a deadline the days cannot cover is a *finding*, listed, not acted on;
- accept everything and run again: the proposal is empty;
- a rejected line is remembered for 14 days and not proposed again for
  that day.

| key       | does                                                        |
|-----------+-------------------------------------------------------------|
| =a= / =r=   | accept / reject the line, or every line in the active region |
| =A= / =R=   | accept / reject the whole day at point                      |
| =C-c C-a= | accept everything                                           |
| =e=       | change the day for this line; it becomes /your/ placement, no stamp |
| =RET= / =o= | jump to / show the entry                                    |
| =g=       | propose again; marks survive on unchanged lines             |
| =C-c C-c= | apply the accepted lines, remember the rejected, propose again |
| =q=       | abandon; nothing written                                    |

Apply is all-or-none: every accepted line is written in its buffer, then
every buffer is saved; an error before that point reverts and reports.  A
buffer with unsaved changes is refused, so save first.  The apply is
logged with its reverse in =.data/org/queue-applies.el=; =,-o-u= plays the
last one back, and is itself logged, so a second =,-o-u= redoes.

An accepted placement is a SCHEDULED stamp with =:PLACED:=.  From then on
the day packer treats it as it treats any schedule: a commitment on its
day (note =placed today=), deferred before it, carry-over after it.  That
is what "pulled in" means once you have accepted it.

* Manual edits

Every change is made on the org entry, or with a write key on its line.
From the plan, =RET= or =o= takes you there; edit; =g= back in the plan.
Four things decide whether a task is /committed, a candidate, or
excluded/: state, SCHEDULED, DEADLINE (with its start-by), and a plain
timestamp.  Once it is a candidate, its score reads priority, IMPACT, age,
effort, and whether it was on an earlier plan; effort is what it costs
its bucket; tags and category decide which bucket.

** Take something off today

Look at the note on the line first; it tells you which lever applies.

- *Scheduled today* → =L= on the line (or =,-o-S= in the entry) to a future
  day.  It becomes deferred.  It can still be pulled forward if its bucket
  underfills.  =U= removes the schedule and it drops back to a candidate.
- *Due today or overdue* → =,-o-D= to move the deadline.  A past deadline
  stays a commitment forever otherwise.
- *Start by today* → the deadline is the lever; or accept that the day is
  the day.
- *NEXT* → =C-c C-t= and set it back to TODO.
- *Chosen by score* → there is no "skip today" gesture.  =H= parks it with a
  note until you change it back.  WAIT with no deadline in the next 7 days
  is also excluded.  Lowering priority nudges the score but may not be
  enough on its own.

** Pull something in

=N= on the line is the designed override: a commitment from you, not a
date.  =S= schedules it on the day and stamps it, which is the same thing
through the date path and is what the proposal would have written.  Both
make it a commitment on the next =g=.  Marking six things NEXT overcommits
the bucket and the plan will say so in as many words.

** Push something back to the backlog

=U= removes a SCHEDULED; =C-u ,-o-D= removes a DEADLINE; =C-c C-t t= takes it
back to TODO.  Leaving a stale SCHEDULED alone is also fine; it only adds a
carry-over bonus.

** Start and finish work

- =C-c C-t p= moves it to PROG.  The timestamp on that transition is when the
  derived clock starts.
- =C-c C-t d= moves it to DONE and stops the clock.  Leaving PROG for any
  other state also stops it.
- A task left in PROG overnight keeps accruing.  The gantt marks such a
  row =~= (provisional) rather than capping it.  Move it out of PROG when
  you stop.
- There is no org-clock.  Do not clock in; the state change is the clock.
- Entering PROG inside the dip starts a timer for the entry's Effort; a
  bell, nothing more.
- =,-o-o j= at a switch writes a journal line linked to the PROG entry;
  any other capture made meanwhile records what it interrupted.
- =,-o-i= hands the entry to an agent: AGENT while it runs, back as NEXT
  (review it: =C-c C-t p=) or QUES.  See "Chains".

** The routine table, read by code

=~/kb/notes/schedule.org= is still the prose note.  Its table gains a
=#+NAME: routine= line and four columns:

#+begin_example
#+NAME: routine
| Time        | Activity               | Notes | kind  | days     | bucket       | habit |
|-------------+------------------------+-------+-------+----------+--------------+-------|
| 05:00–05:30 | Clean apartment        |       | fixed |          | housekeeping | yes   |

  fails with its line number, never with a partial capacity.
- =M-x org-routine-generate-habits= writes =(todo) routine.org= from the

  refuses to overwrite one that does not; IDs survive by title.  The

- =M-x org-routine-report= shows today's blocks, the dip, and the kick /

- The fixture's copy is =testdata/routine.org=; a test session reads it.
- Part 6 question 1 (pomodoros in the dip only, or also block one's first

The real =schedule.org= has not been given the columns yet: until it is,

** Close the day: =,-o-x=

At the fixed stop.  One buffer:

- *Unfinished* -- planned today and still open, each with how many plans
  have carried it.
- *Done today* -- finished today, once each, planned or =unplanned=.
- *Overdue* (hard deadlines) and *Due tomorrow* (tomorrow's, and soft
  deadlines by then).
- *Still in PROG* -- with the captures that interrupted each.  =T= marks a
  line to go back to TODO, =W= to WAIT; =C-c C-c= applies the marks
  together, logged once, undone together.  No note is asked for in the
  sweep; =,-o-z= on the entry adds one.
- *Tomorrow's routine* and *appointments*, the *inbox* count.
- *Tomorrow's draft* -- the same packer run for tomorrow, so it respects
  tomorrow's capacity.  =N= marks a line NEXT; a fourth is refused
  (=org-queue-pick-limit= 3, counted over every open NEXT).
- The phrase.  Printed, not asked.

Closing stamps today in the plan history (=:closed=), once; the next
morning's report says "yesterday closed at 17:02" or "yesterday was not
closed" -- when yesterday had a plan at all; a day never planned gets no
line.

** Dormant projects: =,-o-v j= and =M-x org-queue-dormant-check=

A project is a heading with a child that has a TODO keyword.  It is
*live* when a child is open and not parked (TODO, NEXT, PROG, AGENT, WAIT, QUES)
or the project carries a plain timestamp within =org-queue-dormant-days=
(14); *finished?* when every child is DONE or NOPE; *dormant* otherwise.
The check tags dormant projects =:dormant:= and clears the tag from the
rest; an unchanged corpus writes nothing.  The packer drops a dormant
parent's children with reason =dormant-project=.  The =j= view lists the
dormant and the finished, live, without the check having run.  The check
runs by hand and from the review pack; never from a timer.

** The day log: =,-o-E=

One day in time order: each PROG interval's start and end, every state
change, the captures made that day (joined to the PROG entry they
interrupted, by the =:INTERRUPTED:= property or by time), journal lines.
Under it: the stretches inside a focus or dip block with nothing in PROG
longer than =org-queue-daylog-gap-threshold= (15 minutes), and the
interruptions per block, internal against external.

** The journal line and interruptions

=,-o-o j= captures =* HH:MM what I am doing= under today's =[[Sep 12th, 2026]]=
heading in =~/kb/notes/journal.org= (one file; the heading is created on
first use), with a link to the entry most recently moved to PROG.  Any
other capture made while something is in PROG records that entry's ID as
=:INTERRUPTED:=, which the close counts.  Any plain date in any buffer --
=2026-09-12= or =Sep 12th, 2026= -- is a Hyperbole button opening that day
in the rolo; inside an Org timestamp the button stands aside.

* The week

Built 2026-09-12 (composite.org wave 2).

** The review pack: =,-o-m=

Monday, thirty minutes.  One buffer, sections in a fixed order so two
packs diff readably, assembled from what the files already say:

- the three questions at the top (=w= asks for the answers and writes
  them under today in the datetree of =~/kb/notes/reviews.org=);
- *Moved* and *Finished* in the window (seven days,
  =org-queue-review-window=);
- *Neglected*: every open, unparked item in exactly one bucket by its
  last touch (month, quarter, longer, never; this week's are not drawn);
- *Chase*: WAIT and QUES untouched for =org-queue-chase-days= (7), by
  who has it;
- *Parked, due for another look*: HOLD and IDEA whose =REVIEW_ON= has
  arrived and were not kept since -- raised once;
- *Untriaged*: no estimate, no priority, or no date of any kind;
- the inbox count with its age split; *Dormant projects* and *Finished?*
  (the check runs as part of the pack; =D= reruns it);
- *Still worth it?*: items surfaced =org-queue-dismiss-after= (3) times
  without a pull, proposed for dismissal -- proposed, never automatic;
- *Calibration* when at least =org-queue-calibration-prior= tasks finished;
- *Time by category* from the derived clock, *Against the routine* per
  bucket (under half, over one and a half, or on), and, once horizons
  exist, areas against their floors;
- *Rescheduled*: the ROTTEN count, the sum of "Rescheduled from" lines,
  worst first;
- the chains' week, once there are chains.

Showing a parked item counts as surfacing it: the pack bumps =SURFACED=
on every parked-due and proposed item, in one apply (so =,-o-u= right
after the pack undoes the counters, not a decision).  =g= redraws
without counting again.  =y= on any line asks the question.

** Still worth it?  =,-o-y=

On an entry in an Org buffer, or on any queue line.  Age, plans that
carried it, times surfaced, days since anything happened to it,
reschedules, when it was last kept, and Forster's four questions.  One
key:

| key | writes                                              |
|-----+-----------------------------------------------------|
| =k=   | =KEPT= stamped today, =SURFACED= removed                |
| =p=   | =HOLD= with =REVIEW_ON= a season out (=org-queue-season-days=, 90) |
| =d=   | =NOPE= with =DISMISSED= stamped; the state asks for its note |
| =q=   | nothing                                             |

Each is an apply.  Dismissed is a state, not a deletion: the entry stays
in its file and is never proposed again.

** Decorating the inbox: =,-o-f=

** The confirm gesture

In the Inbox view (=,-o-v i=) the groups are now: captured before
(=DUPLICATE_OF=), proposed with a stale date, proposed, not yet a task, a

| key   | does                                                                          |
|-------+-------------------------------------------------------------------------------|
| =C-c a= | accept: keyword, tags, Effort, IMPACT, dates, WAITING_ON, a Related line, strip every =AI_*=, refile to the target -- one apply, one undo.  On a commit-evidence line: mark DONE |
| =C-c e= | accept one field, chosen by completion; the others are recorded as corrections |
| =C-c r= | reject: strip, stamp =AI_REJECTED= so this prompt does not re-propose        |

* Chains

Built 2026-09-12 (composite.org wave 4).  Most code is written by an
agent you kick off and review; the config now knows it is happening.

** The lifecycle

One new state, =AGENT=, after PROG: an agent has the ball.  You write the
prompt in PROG and kick; the entry is =AGENT= while the run lasts; it
lands as =NEXT= when the run finished (you committed to the review the
moment you kicked it off) or =QUES= when the agent stopped to ask; you
review in PROG; then DONE, AGENT again for the next iteration, or NOPE.
Every hop is a logged transition, so the derived clock gets the split:
PROG intervals are your minutes, AGENT intervals are the machine's,
drawn as the chain's own lane in the gantt (=org-gantt-machine-states=)
and never in a human total; kick to landing is latency, landing to PROG
is review lag, AGENT transitions per chain is the iteration count.

** Kicking: =,-o-i=

On the entry.  The prompt is the body, or the body of a =Prompt=
sub-heading when the entry holds notes too; it is passed to the session
untouched.  Refused without a prompt, or with =org-chain-limit= (3)
chains already in flight -- =C-u= kicks past the limit and the log says
so.  The kick writes =:AGENT_SESSION:= (a UUID), asks once for the
repository (kept as =:AGENT_REPO:=; a decoration's =AI_REPO= is used when
there is one), opens a vterm running =claude --session-id UUID "<prompt>"=
in it, and transitions to AGENT.  =C-u C-u= runs headless instead:
=claude -p= in a git worktree of the repository, output to a buffer.  An
entry with =:KICK_AT: HH:MM= before dawn runs headless only, kicked by a
ten-minute timer when its time comes; an interactive kick of such an
entry is refused.

** Landing

The Claude Code =Stop= and =Notification= hooks run
=~/.claude/claude-landing.sh= (in the .files repo), which appends one
plist per line to =.data/org/agent-landings.el= and nothing else.  Emacs
watches the file (and reads it every minute besides): the entry in
AGENT whose session matches becomes NEXT on a stop, QUES on a question
(the question is appended to the body as "Agent asks: ..."), each line
once, through the apply layer.  A line no entry owns is an orphan,
reported, never dropped.  A stop is a notification unless the routine
says this is a quiet window; a question is a mark in the mode line
(=?2=) and nothing more.

** Where chains appear

- The Day view: *Landed -- review* at the top beside NEXT, *In flight*
  and *Agent asks* after the work in progress.
- =,-o-v a=: the Chains view, the same three groups.
- The morning report: one line -- chains in flight, the landings expected
  in the first focus block at the measured latency and your measured
  cycle, the review minutes they imply, and when fewer chains would do.
- The queue: AGENT is excluded (=in-flight=); a landed entry is planned at
  =org-queue-review-share= (0.5) of its effort -- an agent task's effort
  is your minutes per cycle, spec plus review.
- The close: each chain in flight, primed (its prompt is there) or not.
- The pack: the chains' week -- kicks, latency, review lag, your minutes
  against the machine's.

* Working against the test data

The fixture is eight =(todo)= files under =testdata/todo/=, with full
metadata: efforts, dates, LOGBOOK transitions, IDs, five habits in
=(todo) routine.org= (lift, bike, clean, read, laundry, each with three
weeks of ticks), a dormant project, a finished one, a project serving a
mission and three agent chains in =(todo) work.org=, the season in
=(todo) horizons.org=, =reading= / =housekeeping= tags for the buckets,
and the routine table in =testdata/routine.org=.

1. =M-x zetta-org-toggle-todo-source=.  The echo line should read
   =test (8 agenda files, ...)=.  It rebuilds =org-agenda-files= and the
   HyRolo file list together, so nothing from the real kb is visible.  It
   resets to =real= on restart.
2. The fixture is centred on a date; every stamp is an offset from it.
   Regenerate whenever the centre date has drifted from today, or for a
   clean slate after applies:

   #+begin_src sh
   python3 testdata/generate.py              # centred on today
   python3 testdata/generate.py --today 2026-09-08
   #+end_src

   It is deterministic for a date and seed, and ends by printing what the
   centre day is committed to in raw minutes.  Random dates never land on
   the centre day; what is committed there is pinned by hand in the spec.

A first session that touches every lever:

1. Toggle to test.  =,-o-Q=.  Read the bucket line and the Routine section.
2. =TAB=.  Read the cut and excluded lists and their reasons; =B= to see
   which bucket each task fell in.
3. On a Chosen line, =H=, write a note.  It moves to Excluded.
4. =TAB=, on a cut line, =N=.  It appears under Committed, =next=.
5. On a deferred line, =S=.  Committed, =placed today=; the =d= column shows
   =S <date>*=.  =,-o-u= puts it back.
6. =,-o-P=, "week".  =TAB= on a day.  Find a sliced task.
7. =,-o-p=, "week".  =a= on a few lines, =r= on one, =C-c C-c=.  =,-o-Q=: the
   accepted ones are committed today.  =,-o-p= again: the proposal is
   smaller, and the rejected line is gone.  =,-o-u= undoes the apply.
8. =,-o-w= for the derived clock; =,-o-C= for calibration.
9. =,-o-x=.  Read the sections; =T= on a PROG line, =C-c C-c=; =,-o-u=.
   =,-o-v j= for the dormant project; =,-o-E= for the day.
10. =,-o-m=.  Read the pack; =y= on a parked line, =k=; =,-o-u=.
11. =,-o-v a= for the three fixture chains; =,-o-v d= for "Landed --
    review".  (=,-o-i= opens a real session: try it on a real entry.)
12. =,-o-n=: the season over the fixture's =(todo) horizons.org=; =,-o-v o=
    for the orphans.  On any TODO, =,-o-I= and a date a week out.
13. =,-o-v i= is empty in test mode (the inbox is the real one); =,-o-f=
    and =C-c a= are exercised on the real inbox, with Ollama running.
14. =,-o-M= writes into the real =~/kb/wiki= even in test mode; try it on
    a note you mean to promote.

Every ritual writes (tags, stamps, scores), so regenerate the fixture
afterwards; =source/zettapkg/run-tests.sh= runs every suite and then the
modules over a temporary copy of it.

* Working against the real files

The real corpus is =~/kb/todo/(todo) *.org= plus =~/kb/inbox.org= and the
files in =zetta-extra-agenda-files= (set in =~/.private.el=).

The real files are not yet task files: across nine files there were 1650
headings, 2 SCHEDULED, 6 DEADLINE and no =:Effort:= at the last census.
The queue can only plan what is written down, so the first real step is a
migration.  The tooling exists and has not been pointed at a real file:

- =M-x zetta-org-todo-census= reports what metadata each file has.
- =M-x zetta-org-insert-todo-header= adds the file preamble (Effort_ALL,
  COLUMNS) that column view needs.
- =M-x zetta-org-migrate-checkboxes= converts one buffer: =- [ ]= → =* TODO=,
  =- [X]= → =* DONE=, =- [-]= → =* PROG=.  It shows the count and asks first.
  One undo puts the file back.

Then, in this order, each one a week before the next (the plan's own
gate: would going back be a relief?):

1. The routine table: give =schedule.org='s table its =#+NAME: routine=
   line and the =kind= / =days= / =bucket= / =habit= columns (the fixture's
   =testdata/routine.org= is the model), check =M-x org-routine-report=,
   and =M-x org-routine-generate-habits= for =(todo) routine.org=.  The
   buckets follow from the table; =org-routine-bucket-matches= says which
   tags and categories each bucket claims.  Close the day with =,-o-x=.
2. Monday: =,-o-m=.  The first pack is mostly "untriaged"; that is the
   finding.  =~/kb/notes/reviews.org= is created by =w=.
3. The inbox: Ollama's =qwen2.5:7b= is installed; =,-o-f= sends the inbox
   to it and never leaves the machine.  Set =org-decorate-backend= to
   =claude= if the local proposals are not worth having.
4. Chains: the landing hook is already wired in =~/.claude/settings.json=;
   =,-o-i= on an entry whose body is a prompt.
5. The season: =,-o-n= makes =(todo) horizons.org= from a template; type
   the theme and the missions; =:MISSION:= on the projects that serve
   them.  =,-o-I= before any new deadline.
6. The mail stub: =M-x org-queue-mail-waiting= once flagged mail exists.

Convert =(todo) emacs.org= first, live with it for a week, and only then
decide about the rest.

* What is designed but not built

So this file does not overpromise.  Each item is argued in
=productivity.org= Part 3.2, =time-management.org= Part 6, or
=scheduling.org=.

From =scheduling.org=: sub-day placement into routine blocks, timed
SCHEDULED stamps, round-tripping through the writable timegrid (step 7).

From =composite.org=, whose six waves are otherwise built (above):

- the calendar feed: no external calendar exists to bridge;
- the decoration precision harness (=make decorate-eval=), which needs a
  key and a network, and the decoration idle timer, off until a week
  says the proposals are worth having;
- frequency habits ("three a week"), and the Anki push;
- the Parked view does not count surfacings; only the pack does;
- verified in batch against fixtures and stubs, not yet in the live
  daemon: the timer's ring, the mail reader against the real store,
  decoration against a running model (the request chain was tested with
  a stubbed model), a real kick through vterm and its landing (the log
  reader was tested on lines shaped as the hook writes them), and the
  gate line after =,-o-D=.  Each has a by-name command to try it on
  purpose.

And still: migration of the real =(todo)= files (milestone 5): tooling
exists, not run; and the routine table's columns in the real
=schedule.org=, without which the buckets are the typed fallback.
